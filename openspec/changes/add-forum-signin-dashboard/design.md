## Context

`scripts/自用论坛辅助签到自写.js` 目前按站点策略执行签到：页面进入某个已匹配论坛后，脚本根据 `siteConfigs` 找到对应策略，成功时把 `BBSSignHelperData[site.key]` 更新为今天。这个模型适合“已经打开页面后自动签到”，但不负责提醒用户打开哪些站点，也缺少失败原因、已打开待确认状态和集中结果视图。

用户的浏览器启动时会默认打开 `https://www.limestart.cn/`，因此控制台应只挂载在 limestart 主页上。其他签到网站继续只执行签到逻辑，避免在每个论坛页面增加额外 UI 干扰。

## Goals / Non-Goals

**Goals:**

- 在 `limestart.cn` 提供美观、现代化、信息密度适中的签到控制台。
- 允许用户一键打开今日需要签到的网站。
- 支持独立的可配置打开清单，覆盖“打开后网站自己签到”或“脚本无法检测但仍需每日打开”的站点。
- 保存每日站点状态，并展示成功、失败、已打开待确认、需要登录、需要前台处理等结果。
- 让 SSTM 这类后台标签不稳定站点默认走前台优先路径。
- 兼容现有 `BBSSignHelperData` 成功日期数据，不破坏旧签到记录。

**Non-Goals:**

- 不在 limestart 之外的站点显示完整控制台 UI。
- 不尝试实现浏览器启动级后台服务；脚本仍依赖匹配页面运行。
- 不引入新的第三方 UI 框架或构建流程。
- 不在本次变更中重写所有站点的签到检测逻辑；只在必要处补充状态记录与入口元数据。
- 不扩大论坛站点适配范围，除非是用户配置的打开清单数据。

## Decisions

### Decision: 将 limestart 作为唯一控制台宿主

控制台初始化逻辑只在 `location.hostname` 匹配 `www.limestart.cn` 或 `limestart.cn` 时运行。其他已支持论坛站点继续走现有签到引擎。

备选方案是在每个论坛页面都显示浮动按钮，但这会污染论坛页面，并且仍然无法解决“浏览器启动后忘记打开站点”的主要问题。limestart 是用户固定启动页，更适合作为每日入口。

### Decision: 拆分“签到策略”和“打开目标”

现有 `siteConfigs` 继续表示脚本可执行/可检测的签到策略。新增打开目标模型，控制台从两类数据生成列表：

- 内置目标：由支持脚本签到的站点提供名称、key、入口 URL、建议打开方式和结果模式。
- 自定义目标：用户配置的站点名称、签到网址、是否启用、打开方式、结果确认方式和备注。

这样可以支持“打开网页后自动签到、无需脚本判断”的网站，而不把它们硬编码为签到策略。

### Decision: 状态记录独立于旧成功日期

保留 `BBSSignHelperData` 作为现有成功日期来源，同时新增控制台状态存储。建议状态结构按日期和站点 key 组织，记录：

- `status`: `not-started`、`opened`、`success`、`failed`、`needs-login`、`needs-foreground`、`skipped`
- `stage`: 当前流程阶段，如 `launch`、`navigate`、`find-thread`、`editor`、`submit`、`verify`
- `message`: 可展示给用户的简短原因
- `updatedAt`: 状态更新时间
- `url`: 相关页面 URL
- `attemptCount`: 当日尝试次数

旧数据只回答“今天是否成功”，新状态用于控制台诊断和 UI 展示。实现时可以从 `BBSSignHelperData` 派生今日成功状态，避免迁移失败导致用户看到错误结果。

### Decision: 一键打开按目标特性分流

一键打开只处理启用且今日未成功/未跳过的目标。目标可声明打开方式：

- `background`: 使用后台标签打开，适合 API 或简单页面。
- `foreground`: 打开并聚焦，适合 SSTM 这类需要前台可见状态的站点。
- `manual`: 只在控制台中提供单站打开按钮，不参与批量打开。

脚本可检测目标打开后保持由对应站点策略更新最终状态；自定义目标打开后记录为 `opened`，由用户手动标记成功、失败或跳过。

### Decision: UI 使用原生 DOM + 注入 CSS

控制台使用脚本内原生 DOM 和 `GM_addStyle` 注入样式，不引入新依赖。UI 采用模态弹窗或固定控制台入口：

- 顶部显示今日总览：成功、待确认、失败、未开始数量。
- 主体显示站点列表，使用状态徽标、简短原因、最近更新时间和操作按钮。
- 操作区提供一键打开未完成、重试失败/未完成、编辑打开清单、手动标记状态等动作。
- 配置界面支持新增/编辑/禁用/删除自定义打开目标。

视觉方向应偏现代工具面板：清晰层级、柔和阴影、明确状态色、紧凑但不拥挤的列表、窄屏可滚动且不重叠。

## Risks / Trade-offs

- 后台标签仍可能被浏览器节流 → 对脆弱站点使用 `foreground` 或 `needs-foreground` 状态，并在控制台提供明确提示。
- 自定义目标无法自动判断真实签到结果 → 打开后只标记 `opened`，必须提供手动确认按钮，避免误报成功。
- 新状态结构可能与旧成功日期产生不一致 → 今日成功优先从 `BBSSignHelperData` 兼容读取，并在成功回写时同步更新控制台状态。
- limestart 页面结构未知或未来变化 → 控制台应尽量挂载到 `document.body`，不依赖 limestart 内部 DOM。
- UI 功能变多导致脚本膨胀 → 先实现单文件内的轻量组件函数，不抽象过度；只在重复明显时提取小工具。

## Migration Plan

1. 新增 `limestart.cn` 匹配范围后，在 limestart 页面懒初始化控制台默认配置。
2. 保留现有 `BBSSignHelperData` 不改名、不清空、不迁移。
3. 首次打开控制台时基于内置目标生成默认打开清单，并与用户自定义目标合并。
4. 当站点策略返回成功时，同时写入旧成功日期和新状态记录。
5. 如出现问题，用户可继续访问各论坛页面，现有自动签到能力仍可独立运行。

## Open Questions

- 自定义目标是否需要支持导入/导出配置，还是先只提供本地编辑即可？
- 一键打开时是否需要限制并发数量，例如每次最多打开 5 个标签，避免浏览器瞬间打开过多页面？
- 控制台入口是自动弹出、右下角按钮，还是油猴菜单打开为主？为了减少打扰，默认更适合右下角按钮加菜单入口。
