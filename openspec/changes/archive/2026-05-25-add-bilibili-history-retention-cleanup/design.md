## Context

`scripts/Bilibili视频观看历史记录.js` 已有“历史管理”面板，支持搜索、筛选、排序、分页、导入导出、单条删除和删除选中记录。历史数据由 `StorageManager` 维护，采用 64 个分片存储，单条记录展开后包含 `savedAt` 字符串，现有删除流程通过 `StorageManager.deleteRecord(key, false)` 批量删除后再统一触发 `_notifyChange()` 和界面刷新。

本变更只新增用户主动触发的保留周期清理，不改变记录格式、分片数量、导入导出格式或自动记录逻辑。

## Goals / Non-Goals

**Goals:**

- 在历史管理面板提供“保留 N 天/月/年”的清理入口。
- 只接受数字形式的 `N`，无效输入不执行删除并给出错误提示。
- 计算保留截止时间，并删除 `savedAt` 早于截止时间的记录。
- 删除前通过二次确认对话框明确展示将删除的时间范围和预计删除数量。
- 删除后复用现有刷新、通知和撤销体验，保持列表、统计与页面标记同步。

**Non-Goals:**

- 不新增自动定期清理。
- 不新增按状态、标题、分 P 或当前筛选结果清理。
- 不改变历史记录存储结构、GM key、导入导出 JSON 格式或迁移逻辑。
- 不在开发阶段更新 `@version`、`README.md` 或 `CHANGELOG.md`。

## Decisions

- 将入口放在现有历史管理工具栏中，靠近“导出 / 导入 / 删除选中”等数据管理操作。
  - 原因：这是历史数据管理动作，用户不需要切换到设置页才能执行。
  - 备选：放入设置页。放弃原因是清理结果与历史列表强相关，历史页更容易让用户确认数据范围。

- 使用一个数字输入框加一个单位选择框表示保留周期。
  - 原因：与需求“保留 N 天/月/年”直接对应，UI 简单，且容易做数字校验。
  - 备选：预设 30 天、90 天、1 年按钮。放弃原因是需求明确要求 N 可输入，预设按钮会增加无关选择。

- 截止时间以当前本地时间为基准计算：天使用 `setDate`，月使用 `setMonth`，年使用 `setFullYear`。
  - 原因：与用户对“保留 N 天/月/年”的直觉一致，并能自然处理月份和闰年。
  - 备选：统一换算为固定毫秒数。放弃原因是“月/年”的长度并不固定，固定毫秒数容易产生边界误差。

- 删除候选范围为所有历史记录，不受当前搜索、状态筛选、排序或分页影响。
  - 原因：按钮语义是按全量历史保留周期清理；若只清理当前筛选结果，确认文案和用户预期都更容易混淆。
  - 备选：仅清理当前筛选结果。放弃原因是需求未要求，且会增加规则复杂度。

- 二次确认使用同步确认对话框或现有面板内确认能力，确认内容必须包含截止时间、删除范围描述和预计删除数量。
  - 原因：实现小、风险低，并满足“二次确认对话框，明确删除的时间范围”要求。
  - 备选：新增完整自定义确认弹窗。可在实现时根据现有 UI 成本决定，但不应引入复杂弹窗框架。

- 批量删除复用现有 `deleteRecords(keys)` 流程，或抽取一个共享批量删除 helper 给“删除选中”和“保留周期清理”共用。
  - 原因：现有流程已经处理备份、撤销、通知、选中状态清理和刷新，复用可降低行为分叉。
  - 备选：为保留周期清理单独写删除逻辑。放弃原因是容易遗漏撤销或同步通知。

## Risks / Trade-offs

- `savedAt` 为空或解析失败的旧记录可能无法可靠判断时间 → 默认不作为过期候选删除，避免误删。
- 大量历史记录下全量扫描可能短暂占用主线程 → 该功能由用户主动点击触发，且复用已有 `getAllRecords()` 全量读取能力；实现时避免在输入变化时实时扫描。
- 月份边界可能出现“31 日减 1 个月”这类日期归一化 → 采用浏览器 `Date` 的本地时间计算，并在确认文案展示实际截止时间，让用户看到最终边界。
- `window.confirm` 样式不可定制 → 换来更小实现和更稳定的二次确认；若现有 UI 已有轻量确认弹窗，可在实现时使用同等语义的面板内对话框。
