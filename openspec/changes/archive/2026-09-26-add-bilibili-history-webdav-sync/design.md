# Design

## Context

动机见 proposal.md。已检查目标脚本、README 对应分区、存储一致性／管理面板／保留周期规范及现有测试 harness：

- `HistoryCommitStore` 已提供 `[逻辑时间, writer, sequence]` 版本排序、`deleted` 标记和不可变事务提交；无需为云同步重写本地存储。
- `StorageManager.getAllRecords()` 只返回可见记录；普通导入跳过已有记录，`saveRecords()` 部分来源会分配新版本，均不能直接承载云端合并。
- 播放页按需读取，云同步必须显式全量加载后取快照，不能上传局部缓存。
- `BvH_backup_` 是七天 localStorage 临时恢复机制，不是用户日期备份。
- 管理面板已有维护分类、草稿、确认弹窗与错误反馈；AppController 已管理启动、SPA 和页面可见性。
- 已有 Node VM 隔离存储及并发测试，可扩展网络模拟，不新增测试框架。

## Goals / Non-Goals

**Goals:** 在单脚本内增加小型 WebDAV 请求层、同步协调器和独立云同步模块；复用本地提交与 UI；让同步、备份和回滚结果可解释、可验证。

**Non-Goals:** 不做实时协作、逐操作增量同步、服务端程序、设备管理面板、分布式锁、无限重试、逐条冲突编辑或端到端加密。只同步观看历史及必要元数据；不支持任意 WebDAV 厂商私有认证协议。

## Decisions

### 1. 小索引、不可变压缩快照与独立备份目录

用户分别填写 WebDAV 地址与相对保存目录。保存目录可留空；脚本会逐级创建填写的目录，再在其下创建固定的本脚本专用子目录。地址本身可以包含服务所需路径（如 `/remote.php/dav/files/user/`），但不与保存目录合并成一个输入框：

```text
<WebDAV 地址>/<保存目录>/bilibili-history/
  state.json
  history-<uuid>.json.gz
  backups/
    daily-2026-09-26.json.gz
    before-restore-20260926T083000Z-<uuid>.json.gz
    before-resync-local-20260926T083000Z-<uuid>.json.gz
    before-resync-cloud-20260926T083000Z-<uuid>.json.gz
```

历史正文采用 gzip 压缩的全量紧凑 JSON；state.json 是唯一的当前版本入口，不压缩，包含 format、schemaVersion、snapshotId（UUID）及 file（严格为 history-<同一UUID>.json.gz）。不包含记录列表、凭据或不断增长的版本日志，目标正文小于 1 KB。UUID 只比较相等，不表示时间顺序，不替代回滚 epoch 或删除回收 revision。索引内文件名不得是绝对 URL、带目录分隔符或跳出专用目录。每次实际内容发布生成新 UUID，历史正文也携带该 snapshotId；文件上传后不再修改或重新成为未来发布目标，回滚也生成全新文件。小索引和正文采用第 3 节的先正文后索引流程，不引入分片、增量日志或备份索引。使用 PROPFIND Depth:1 列举备份，文件名识别归属；不递归扫描用户目录。每日文件使用 UTC 日期，界面明确标注 UTC 日期及本地显示的实际创建时间。

使用原生 `CompressionStream('gzip')`／`DecompressionStream('gzip')`，以二进制文件体上传，下载采用 ArrayBuffer；不转 Base64，不设置让服务端自动解压的 Content-Encoding，把 gzip 字节作为文件保存。JSON 不缩进，保持对象字段及规范化顺序；不用自定义二进制、字段字典或差分备份链。gzip 后字段名重复本身已被压缩，改成数组仅再节省少量空间，却增加格式维护负担。功能启用时检查原生能力，不支持则提示云同步不可用，不新增依赖或静默写另一种云格式。

压缩测量使用 10 万条合成记录、随机 BV 编号、约 3000 个写入者及约 30 字标题，Node gzip 默认参数估算，未冒充真实用户数据：

| 合成样本 | 未压缩 JSON | gzip | 数组化后 gzip | Brotli quality=5 |
| --- | ---: | ---: | ---: | ---: |
| 词汇组合标题及数字 | 24.26 MB | 4.82 MB | 4.52 MB | 4.84 MB |
| 6000 常用范围汉字随机组合 | 25.46 MB | 9.73 MB | 9.48 MB | 8.13 MB |

随机汉字样本用作较难压缩的对照，不是保证的上限；浏览器 gzip 参数、真实标题及版本分布会改变结果。规划量级按 5～10 MB／份估计，默认 7 份每日备份加最新快照约 40～80 MB，另计待清理旧同步文件、操作前备份、删除标记和服务商文件版本。Brotli 在这两组样本未表现出一致的巨大优势，首版不增加第二种编码；普通手动导出仍为原 JSON。

快照包含 `format: "bvh-webdav"`、`schemaVersion: 1`、`snapshotId`、`epoch`、`revision`、`minSyncRevision`、`createdAt`、`kind`、`backupRetentionDays` 及 `entries`。revision 在无并发覆盖的同步序列内，是当前 epoch 每次成功发布索引加一的整数，minSyncRevision 初始为 0，记录回收后允许正常合并的最低已采用修订号。活跃条目仅保留规范化 key、紧凑 record 和原 version；删除项不携带 record，只携带 key、version、deleted、首次云端发布时的 `publishedRevision` 和 `publishedAt`。不上传事务块、container、凭据、日志、显示设置和本地撤销窗口身份。普通 JSON 导出仍只有公开记录，不改变原菜单语义。

`epoch` 初始为固定 `initial`，每次全设备回滚生成新 UUID。同一 epoch 按版本合并；跨 epoch 采用云端当前批次。独立回滚文件不直接作为当前快照发布，而是生成新 epoch 的恢复结果。

备份允许包含尚未发布的本地删除（没有 publishedRevision），但 索引引用的正式快照中的删除必须带有效首次发布信息。恢复旧备份时提取有效记录集合，生成新 epoch 与新版本，不把旧批次的 revision／minSyncRevision／删除发布信息带入新批次；本地替换所需删除项属于本地过渡提交，不能当作旧批次删除重新上传。

### 2. 标准请求与可选条件写入

增加薄封装 WebDavClient，采用 `GM_xmlhttpRequest`、用户名／应用密码，支持 GET、PUT、PROPFIND、MKCOL、DELETE 及可选 HEAD。单次请求超时建议 30 秒，处理认证、HTTP 状态、超时、解压和解析错误，不引入 SDK、远端锁或循环重试。新增所需 GM 请求权限及 `@connect *`，正文、索引、备份和探测请求限于自动生成的脚本专用子目录，目录创建请求只访问其父路径；地址不接受内嵌凭据，保存目录不接受绝对路径或 `..`，日志不记录认证信息；保持原 @match、@require。

测试连接使用唯一临时文件验证基本读写、列举和删除，finally 尽力清理，不修改 state.json 或正式历史。分别探测强 ETag、If-Match、If-None-Match 的实际行为，不能仅凭响应头认定支持。HEAD 不可用时用 PROPFIND 或 GET，不作为连接门槛。认证失败、超时或含糊结果不能被当作能力缺失。

具备可靠条件能力时，对 state.json 的更新携带本轮读取到的 If-Match，首次创建使用 If-None-Match:*；412 结束本轮，下一轮重新读索引，不去掉条件头覆盖。不支持时对索引普通 PUT，仍可凭 UUID 跳过未变历史正文。正文使用唯一文件名，两种路径都不覆盖旧正文；ETag 只增强索引发布的并发保护，不承担基本变更检测。

**用户已确认的边界：** 无条件写入时多设备同时发布索引仍可能后写覆盖先写，影响合并、共享设置、回滚和删除清理进度。revision 在竞争中可重复或倒退，不能当作全局提交证明；发现修订倒退或同号不同内容使旧基线失效，有清理进度时进入既有二选一。这只能处理已观察异常，不能保证竞争下绝不丢失或复活记录。写后读回、UUID 和操作前备份均不提供原子并发保证。模块静态显示兼容限制，不反复弹提示，不增加技术开关。增强模式也不保证与绕过条件写入的外部客户端并发安全。

协议参考：[Tampermonkey 请求 API 与权限](https://www.tampermonkey.net/documentation.php?q=GM_xmlhttpRequest)、[WebDAV RFC 4918](https://www.rfc-editor.org/rfc/rfc4918.html)、[HTTP 条件请求 RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)、[浏览器原生 Compression Streams API](https://developer.mozilla.org/en-US/docs/Web/API/Compression_Streams_API)。

### 3. 先读小索引，按需传输正文

新增 StorageManager 的完整云快照读取、按原版本应用及完整替换接口，不使用普通 importRecords() 或会重标版本的保存路径。写入复用既有提交、队列和通知机制；网络与 Worker 不占用播放保存队列。

每轮直接 GET state.json，要求绕过缓存／重新验证，不把浏览器缓存当作最新云端；无需先 HEAD 再 GET。完整校验索引及文件名，取其 UUID 与本地 lastAppliedSnapshotId 比较。只有本地已完整采用该文件并保存有效基线时才可跳过正文；仅看到索引、仅下载成功或部分应用不能记录为已采用。缺少基线、改服务器、恢复中断时须读取正文，不因 UUID 恰好相同跳过必要恢复。

| 索引 UUID | 本地待同步变化 | 本轮历史正文传输 |
| --- | --- | --- |
| 与已采用版本相同 | 无 | 不下载、不上传；仅小索引及必要维护请求 |
| 与已采用版本相同 | 有 | 基于已采用完整状态生成并按需上传，不下载旧正文 |
| 不同／无已采用基线 | 无 | 下载索引指定文件，校验并应用，不重复上传相同内容 |
| 不同／无已采用基线 | 有 | 下载后按原版本合并；结果不同才上传 |

本地变化跟踪复用提交身份／清单和 onDataChange 通知，涵盖新增、进度、删除、保留清理、导入、回滚及跨页写入；共享保留设置另有待发布标记。通知仅用于及时失效，不能作为唯一完整性证明，不使用跨页读改写的单一 dirty 布尔值或计数器。到期先核对轻量提交基线；重启、通知遗漏或整理后无法证明基线完整时全量读取本地并计算规范化摘要，可不下载同 UUID 的远端正文。同步捕获本轮提交边界，成功只确认这一边界内的修改，上传期间的新提交仍待同步；纯云端应用不制造上传回声。未到期仍只查调度状态。

需要下载时，对指定 history 文件 GET、解压、整体校验，确认 snapshotId 与索引一致，再执行原有 epoch／minSyncRevision 判定与 HistoryCommitStore.compare() 合并。相同版本不同内容拒绝，普通同步不重标旧记录版本。正文缺失、损坏或 ID 不匹配时停止，不当作空历史、不发布索引；下轮重新读索引以处理并发切换或清理，不循环重试。首次初始化只在 state.json 确实 404 时进行；遗留未引用 history 文件不自动选作正式历史。

内容摘要排除 snapshotId、createdAt 和检查时间，包含历史、删除、epoch、revision／清理进度和共享保留设置等实际语义。先确定确有业务变更，才分配新 revision 与 UUID；不能因生成了 UUID 自己触发更新。发布顺序固定：完整上传全新 history-UUID.json.gz，成功后按第 2 节能力 PUT state.json，索引成功后才推进本地同步基线、删除发布确认与回收进度。正文上传失败绝不发布索引；索引失败不算同步完成，保留本地待同步状态，未引用正文交给清理。索引请求超时可能已经成功，下轮先读取并核对当前索引及必要正文再确认，不回滚索引，也不重用旧文件进行延迟发布。页面重启、任务取消或任务持续超过 10 分钟时重新读索引并以新 UUID 开始发布；避免长期挂起任务继续发布旧候选。

每日备份先用目录列举或 HEAD 判断当日文件，已有则不重传。不存在时从已确认的完整云端视图生成独立压缩备份；若本地能证明与该视图相同可重建，否则按索引读取正文，不能把尚未同步的本地修改混入。备份自包含而非指向 history 文件的链接。条件创建可用时用日期固定文件名和 If-None-Match:*，412 作为已有；否则日期＋时间＋UUID 命名，同日并发多份如实列出。备份失败单独记录待重试，不撤销已完成同步；备份成功或已存在后，按云端 N 清理过期备份。

**旧同步文件清理：** 成功同步后的每日维护列举本脚本根目录，读取最新有效索引，保留它指向的文件；仅对可识别且服务端修改时间已超过 24 小时的未引用 history 文件清理，覆盖索引失败遗留的孤立文件。清理前再次核对小索引，变化则跳过本轮清理；无法可靠判断时间或读取索引失败则不删，模块记录维护失败。24 小时是固定内部缓冲，与默认 7 天备份及 30 天删除窗口独立，不加设置项。旧读取者遇到文件已清理时下轮重新取索引，不能持有旧文件名直接发布；恢复备份始终生成新文件。正常服务和脚本客户端下，旧文件只随最近缓冲期的更新量增长，不按历年更新总数增长；不承诺异常服务或无条件并发下的绝对原子清理。

**流量与占用：** 无变化时，两种能力模式都只下载通常小于 1 KB 的索引正文及必要元信息；HTTP、TLS 和认证开销另计。仅本地变化上传一份约 5～10 MB 的压缩正文和小索引，远端变化下载一份，两端变化约各一份，新增每日备份另上传一份。删除到期、共享设置更新等维护也可能产生新快照。默认 7 份备份＋当前快照约 40～80 MB，另有清理缓冲内旧正文：单设备全天每小时确有变化时可额外积累约 24 份即 120～240 MB，实际取决于更新次数、维护时机和多设备数量；没有变化不产生新正文。无变化时不再产生每小时全量下载；40～80 MB 也不是全部空间上限。

### 4. 全设备回滚用一个批次标识隔离旧数据

用户已确认回滚影响全部设备、替换离线设备未同步的旧记录。只对记录逐条写较新删除标记无法排除尚未上传过的离线记录，因此选用 epoch，不引入操作日志或每设备确认表。

恢复流程：读取并完整校验选中备份与最新云端，显示备份时间／条数／全设备影响并确认；短暂停止当前页面采样提交，取本地和云端当前批次的合并快照，PUT 唯一命名的 before-restore 备份；该步骤失败不得改正式历史。随后为选中备份生成新 epoch，按第 3 节上传全新正文并发布索引：有条件写入时对索引携带刚读到的 ETag，否则在备份后重新 GET 索引核对 snapshotId 再普通 PUT；发现变化或冲突结束本轮，保留恢复前备份。云端成功后本地提交完整替换，并记录已采用 epoch，最后恢复采样。

本地替换以一批事务写入目标记录和当前多余记录的删除项，为所有替换项分配高于已观察本地版本的版本值，保留目标记录中的原 savedAt 和进度。对外发布的恢复快照使用同一组新版本。其他设备采用快照时，因自身逻辑时钟可能更大，可在本地替换接口内分配更高的本地提交版本；后续上传只携带属于新 epoch 的完整视图，不合并旧视图。

为区分“已完成替换”与中断，替换事务清单携带云端目标标识与 epoch，成功提交后再更新 `bvh_webdav_state`；重新启动从已确认替换提交恢复 epoch，不能仅凭状态 key 判断成功。后台整理必须保留最新已提交批次标识，空历史回滚也必须能提交该标识。旧事务无此字段仍兼容。此处复用现有事务完整性，不实现网络与 GM 的跨系统原子提交：云端已成功而本地失败时明确提示，并在下次同步先应用云端批次。

本地需要一个当前历史 epoch 标记，普通写入在入队前捕获它，提交前检查未变化；已更换批次的旧页面重新加载历史、丢弃旧待保存采样。临时备份附带 epoch，首次回滚前兼容没有 epoch 的旧备份，回滚后不恢复旧批次临时备份。替换事务与其他标签页正常写入使用既有提交 guard 检查重评估，避免先清空再逐条导入。活跃播放只从确认新批次后的新采样继续保存。

已关联此远端的设备发现用户显式全局回滚导致 epoch 改变时先完整替换，不上传旧本地视图，这是此前已确认的全设备回滚语义。首次连接有本地数据的设备若云端 minSyncRevision>0，则优先执行第 6 节的二选一；本地已处于另一个回滚批次、云端却仍为 initial 时也先二选一，避免切换目录时混合两套完整历史。其余无清理缺口的初始批次可按原版本合并；云端已明确处于新回滚批次时按全设备回滚语义采用云端。恢复前备份可按相同流程再次恢复，不提供另一种专用撤销协议。

### 5. 简单调度和界面

配置用 `bvh_webdav_config`，运行状态用 `bvh_webdav_state`，按规范化 WebDAV 地址、保存目录及脚本专用子目录隔离最近成功时间、远端 epoch、已完整采用的 revision、lastAppliedSnapshotId、本地提交基线、可用索引 ETag 和内容摘要，改地址或保存目录后重新识别远端，不能复用原远端状态。凭据变化不清空观看历史。

`backupRetentionDays` 默认 7，接受正整数 N，对同一云目录为共享设置。首次创建云端使用已保存值；其他设备读取云端值，不用安装默认值覆盖。用户显式修改后本地记录待发布设置，下一次成功同步写入云端才生效；冲突时保留草稿意图并提示重试，清理始终采用最新确认的云端值。缩短天数的设置说明提前告知会清理超期备份。手动回滚历史不回滚当前保留设置。N 与本地观看历史清理周期独立，也不决定删除标记的回收窗口。

自动频率默认 off。用单个低频检查器（建议每分钟）配合启动与 visibilitychange 检查最近成功时间，hourly=1 小时、daily=24 小时；失败后至少 5 分钟再试。不做整点任务、错过次数队列或关闭浏览器后的定时承诺。未到期不全量加载历史。

当前实例用一个 in-flight Promise 合并重复任务；多个标签页共享下一次到期时间，并用带随机实例 ID、短有效期和执行中续期的 GM 占用记录减少重复发起。到期前仍先核对共享最近成功与占用状态；占用过期后其他页面可接替，任务结束或页面销毁时释放自己的占用。占用只减少常见重复流量，不把非原子的 GM 读写包装成分布式锁：极短时间内跨标签页仍可能同时请求，有条件写入时拒绝基于旧快照的覆盖，兼容模式接受第 2 节的并发限制；遇 412 重新读取共享成功时间，不覆盖另一实例已记录的成功状态。销毁时清理计时器及监听，SPA 不重复初始化。

新增 `cloud` 页，与现有偏好设置、历史管理、数据统计并列为第四个导航模块，标题为“云同步”；设置内的四个原有分类保留，云端配置不放在维护分类。保留默认打开设置页，静态待处理入口可直达云同步页。模块使用独立云配置草稿和“保存云同步配置”操作；切换模块保留所有未保存草稿，关闭时沿用保存／放弃／继续编辑流程。保存云配置不意外提交其他设置草稿，恢复普通界面默认值不抹除 WebDAV 账号。连接测试直接使用当前草稿，不保存配置；测试连接、手动同步、恢复等主动操作使用脚本统一 toast 展示进度及结果，页面标题区不显示这些操作反馈。立即同步和备份列表使用已保存配置，未保存云配置执行同步时给出 toast 说明。

界面定位为与现有工作台一致的现代、克制的数据管理页，沿用深石墨导航、暖白背景、蓝色主操作、既有字体层级和间距，不新建另一套主题或引入远程字体。复用 `--bvh-*` 色彩变量、SVG 图标笔画、细边框、圆角与轻阴影。上方为宽幅同步状态区（状态文字、最近成功时间、同步频率摘要、立即同步主操作），中部桌面两栏为“连接配置”和“同步与备份策略”，下方全宽为按日期排列的备份列表；窄屏顺序堆叠，四项导航可换行或采用紧凑布局，不挤压成整体横向溢出。状态区不展示虚构进度或流量指标。

连接表单分别提供 WebDAV 地址与相对保存目录，并实时展示相对 WebDAV 地址的脚本专用路径，如 `/bilibili-history/` 或 `/脚本备份/bilibili-history/`；还提供用户名、应用密码、密码显隐和次级“测试连接”。测试期间按钮显示运行状态，统一 toast 展示进行中、成功或失败；深色状态区标题必须保持可读对比度。策略区的关闭／每小时／每天使用定制分段 radio 组选项，保留天数使用带“天”单位的统一输入，可附 7／14／30 天快捷按钮，任意正整数仍可直接输入。备份区采用统一行高的日期列表与来源标签，每项显示实际时间、条数（未读取时不编造）及恢复入口，展开详情才读取必要文件，不为展示列表预先下载所有备份。首次同步前专用目录不存在时，即使服务对目录列举返回 409，也显示正常空备份状态；已有索引却无法列举备份目录时保留错误。未配置、空备份、加载、失败和待选择均有专门文案与完整布局，不把信息全部堆在一张长表单中。

控件保留 input、button、radio 等基础 HTML 语义及密码管理器能力，由脚本 CSS 统一外观；避免未经设计的原生 select、数字 spinner、日期弹框。不用 contenteditable 伪造文本框，不引入组件库或通用下拉框框架。恢复与本地／云端选择复用 `WorkbenchLayers` 自有弹窗，后者用两张可选方案卡展示来源、数量与影响，不使用原生 alert／confirm／prompt。定义 hover、focus-visible、selected、disabled、loading、error 状态，保持对比度和焦点管理；减少动态效果偏好下关闭非必要过渡，日常状态无持续动画。

独立模块的状态区分别展示同步与备份结果；所有自动任务的进度、成功和错误都只更新这里，不弹 toast、模态框、系统通知，不播放声音、不抢焦点。重复错误合并为最新错误及时间，不累计消息列表或每次重试刷屏。手动操作在当前模块操作区展示一个任务的进度与结果，不为内部每个阶段分别弹通知；关闭面板后不自动重开或补弹结果。状态变化只更新对应字段，不重建表单或丢失焦点、草稿和滚动位置。

### 6. 删除标记回收与旧设备二选一

不能只按视频 savedAt 或设备最后联网时间删除标记：一条数年前的记录可能刚刚被删除，设备也可能可以看 B 站却长时间无法连接 WebDAV。采用“删除首次发布修订＋清理进度”的有限窗口，不维护永久设备登记表或逐设备确认矩阵。

**云端回收：** 删除首次进入云端时记录 publishedRevision、publishedAt；再次传输同 key／version 不刷新这两个字段。本地旧删除首次上传也从首次成功发布开始计满 30 天，不能按本地删除时间立即过期。每日成功同步维护时，从最新云端状态筛选到期标记，移除并将 minSyncRevision 推进到已回收删除项 publishedRevision 的最大值；revision 加一，与条目一同放入新快照，正文上传后发布索引，不单独写清理进度文件。发布失败就不推进本地回收。没有到期删除则不因维护时间变化生成新正文或更新索引。

**正常设备：** 在同 epoch 内，只有本地已完整采用的远端 revision >= minSyncRevision，才能继续原版本合并。该关系意味着设备已见过被回收的删除结果。对于曾成功发布、如今已被进度覆盖且云端不再存在的同版本删除，本地也移除，不把它当作新删除再次上传。只保留窗口内的删除确认信息；本地尚未发布的新删除版本不受影响。设备仅因时间久而未同步、但实际没有错过被回收删除时，仍可正常同步。

**过旧设备：** revision 不足或缺少基线且已有云端清理进度时，先暂停当前设备自动合并和上传，在面板中显示“云端已清理过旧删除信息，请选择保留哪一份历史”。面板未打开时仅在既有入口保留一个静态待处理标记，不自动弹窗、不闪烁；入口隐藏时仍可从脚本菜单进入。用户主动打开处理区后才展示两个选项，不预选，关闭后保持待选择。本地继续正常记录，下次打开选择面板重新读取双方数量和时间。不是自动采用云端，也不是把未同步的新记录偷偷丢弃。

- 使用云端：确认后分别上传本地和云端的两份 before-resync 备份；两份均成功且复核未发现双方变化，才完整采用云端并记录当前 revision，不重置云端 epoch，也不覆盖云端历史。
- 使用本地：同样先备份两边；以本地当前有效记录集合为准，丢弃历史删除项，发布全新 epoch、revision=1、minSyncRevision=0 的最新快照。复用显式回滚流程，其他已关联设备下次采用该批次。确认文案说明云端独有记录会退出当前历史，本地旧记录可能被主动恢复。
- 任一备份失败、确认后本地变化、索引 ETag 改变或兼容路径复核 snapshotId 变化时不执行覆盖，提示刷新后重新选择。选择前备份标注 local/cloud 来源，使用现行 N 天保留策略，可作为日期快照恢复；不回滚共享保留设置。

**本地实际释放：** 复用现有 checkpoint 整理，但允许省略已确认传播并由 minSyncRevision 覆盖的删除项。新本地基线需保留清理进度、已覆盖提交范围和一个本地写入代次；先验证替代基线完整，再删除被覆盖旧块，清理短期删除确认信息。与清理并发产生且未覆盖的新提交继续保留。迟到的旧事务／采样按基线范围及捕获的写入代次识别并拒绝，不靠已经移除的逐视频删除项兜底。当前页面重新读取后以新代次正常写入。写入代次和本地备份代次在关闭 WebDAV 后仍有效，不允许关闭同步使旧内容复活。

这部分需要适配现有提交读取与整理，而不只是删一个数组元素；任务必须验证存储块实际缩小以及多页中断恢复。不能以“云文件变小”冒充“本地占用已回收”。关闭云同步或长时间不同步时，不回收尚未确认传播的删除；仅在实际同步维护运行后才释放空间。

完成维护后，云端主文件的删除开销主要由最近 30 天已发布删除决定，本地主要为同窗口删除及尚未同步操作，过期备份清理后不再按历年累计删除数增长。有效历史持续新增、短期集中删除、更多恢复前备份或服务商自己的版本留存仍会增加占用，不能承诺固定 MB 上限。

### 7. 无感运行的执行边界

每轮需要全量计算时按需创建一个临时 Worker，在其中执行 JSON 序列化／解析、规范化排序与合并计算、摘要和 gzip 编解码；不引入 Worker 池、常驻服务或额外库。脚本内嵌 Worker 代码，任务结束、异常及页面销毁时 terminate 并释放 Blob URL、ArrayBuffer 和临时对象。GM 请求和持久化仍由可访问 GM 的脚本上下文负责。通过分批消息搬运记录、transferable ArrayBuffer 搬运二进制结果，避免主线程一次 structured-clone 整个 10 万条对象；Worker 只回传所需差异／分批结果，不重复回传全量 JSON 和对象副本。

主线程的 GM 读取、输入整理与最终数据应用复用现有分批让出机制，单次同步计算片段以约 8 毫秒为目标，及时让出事件循环处理播放器、滚动及输入。启动到期任务在当前视频监听及本地保存初始化后低优先级安排，不把云同步放入启动必经等待链；播放中也可执行，不要求等用户停止观看。网络和 Worker 阶段不得持有本地保存队列，最终写入只沿用必要事务边界，保留新采样。不能通过暂停播放器、禁用输入或长时间停止进度采样换取同步顺利。

未到期计时器只检查少量状态，不计算全量摘要、不创建 Worker。到期后才核对变更并按需生成完整视图；远端确认不变且本地已证明无变化时复用已确认摘要，避免为了“跳过上传”仍反复做全量序列化。自动任务状态只更新相关面板字段，不周期性重绘整个面板、重新查询历史或扫描页面。已建立相同源实例任务合并；跨标签页有条件写入时拒绝冲突，兼容路径接受第 2 节的限制，不为性能优化增加分布式调度。

Worker 创建失败或所需原生能力不可用时，不退回主线程一次性处理 10 万条记录。结束本次云任务，释放资源，将原因记录到面板；配置／环境能力问题不每分钟重新做高成本初始化，用户手动重试或下次页面启动再检查，本地功能照常。

性能验收关注真实浏览器内的交互响应而不只看压缩耗时。以 10 万条记录覆盖首次拉取、仅本地变更、双向合并、备份与回收，在视频播放中测试滚动、进度条、面板输入和关闭；记录云同步引入的主线程长任务、交互延迟、内存峰值及任务结束资源释放。控制测试环境中以不新增超过 50 毫秒的脚本主线程连续计算为检查目标，达不到时定位并拆分，不把 Node 中的几百毫秒 gzip 耗时当成浏览器无卡顿证明；浏览器／低配设备实测不足时如实说明。

## Risks / Trade-offs

- 全量快照带来网络与序列化成本 → gzip 压缩、小索引 UUID 与稳定本地基线跳过未变正文；依然不做增量分块，解压后的内存和本地 GM 大小不会自动按压缩比例缩小。
- WebDAV 服务能力不同 → ETag 与条件写入按能力启用，缺少时采用用户已接受的简单兼容模式。UUID 索引让无 ETag 服务也可跳过未变正文；没有条件写入时竞争可能覆盖历史、回滚与删除清理进度，不以事后校验或备份冒充并发保证。实际服务实施阶段分别验证两种路径。
- 删除标记与旧提交持续增长 → 30 天云端窗口、少量清理进度和本地 checkpoint 回收；失去同步基线的设备由用户二选一，备份两边后再执行。
- 设备时钟偏差影响首次冲突顺序 → 沿用现有逻辑版本并吸收远端时钟，不增加时间服务器；界面说明按记录版本合并。
- 回滚会替换离线未同步内容 → 已由用户确认；恢复确认明确提示，恢复前备份只覆盖当时可见的本地与云端数据，不能声称备份了离线设备的数据。
- 云端和本地无法一步原子完成 → 阶段反馈及下次先采用新 epoch，避免假成功；沿用已有本地事务处理崩溃中断。
- 浏览器后台节流及不同日期时区 → 定时为尽力执行、UTC 日期备份标注清楚，不假装提供指定时刻的精确快照。

## Migration Plan

新增功能默认关闭，不迁移或改名既有历史／设置 key。旧事务及临时备份保持读取能力；成功回滚或本地删除回收基线覆盖的旧采样、临时备份不再自动写入。普通 JSON 导入导出不增加云元数据。该功能尚未发布，直接采用 .json.gz 格式，不实现从先前提案中未上线 .json／latest.json.gz 云文件的迁移。

实施不自动升版或改发布文档。用户要求收尾时按新增功能递增次版本，更新目标脚本 README／CHANGELOG 和元信息。关闭云同步即可停止请求，保留本地记录与云端备份；功能回退前可按原格式导出记录。旧版不理解回滚批次，不能与新版混用云同步协议。
