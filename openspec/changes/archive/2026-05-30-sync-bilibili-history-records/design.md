## Context

`Bilibili视频观看历史记录.js` 当前通过播放器事件记录本设备的视频访问与观看进度，记录格式包含 `status`、`currentTime`、`percent`、`savedAt`、`title`，并通过 `StorageManager.saveRecords` 批量写入分片存储。脚本已经匹配 B 站历史页，但历史页目前只用于显示本地标记，不会把 B 站账号历史记录反向同步到脚本记录中。

用户提供的 `temp.html` 卡片示例显示，当前 B 站历史页卡片主要结构为 `.history-card.grid-mode`，卡片上有 `data-bsb-bvid`，视频链接中可能带 `p=` 分 P 参数，标题在 `.bili-video-card__title a`，观看进度可来自 `.bili-cover-card__stat span` 的 `01:01:14/01:17:14` 或“已看完”，也可来自 `.bili-cover-card__progress` 的 `--bili-cover-card-progress-value`，观看时间在 `.bili-video-card__corner span`，旁边是电脑或手机图标。

## Goals / Non-Goals

**Goals:**

- 在 B 站历史记录页提供一个独立于页面布局和脚本历史管理面板的悬浮同步按钮。
- 首次点击同步当前已加载历史卡片；同步后按钮变为继续同步。
- 用户再次点击继续同步时，脚本自动滚动到底部，等待 B 站加载更多卡片并稳定后再次同步；后续点击重复此流程。
- 从当前已加载的历史卡片中提取视频 key、分 P、标题、观看进度、观看时间。
- 将 B 站历史记录合并到脚本本地分片存储，并复用现有 UI 刷新与批量保存能力。
- 进度合并以更长观看进度为准；进度差距在 5 个百分点以内时完全跳过，不更新进度或观看时间。
- 同步完成后给出新增、更新、跳过和失败数量反馈。

**Non-Goals:**

- 不自动请求 B 站历史 API，也不新增 `GM_xmlhttpRequest`、`@connect` 或外部依赖。
- 不在一次点击中无限自动滚动全量同步所有历史；每次继续同步只执行一次“滚到底部、等待加载、同步已加载卡片”的循环。
- 不改变现有导入、导出、删除、保留周期清理和播放器自动记录行为。
- 不处理无法解析出脚本视频 key 的非视频类历史记录。

## Decisions

1. 同步入口使用历史页悬浮按钮，而不是历史管理面板工具栏。

   理由：用户希望同步行为跟随 B 站历史页本身，并且后续继续同步需要在页面滚动过程中保持可见。按钮应作为脚本自己的视口悬浮层存在，不嵌入 B 站历史列表 DOM，也不放进脚本历史管理工具栏。

   建议状态：

   ```text
   同步当前页面 -> 同步中... -> 继续同步
                         ^           |
                         |           v
                    等待加载... <- 自动滚到底部
   ```

2. 同步来源使用历史页 DOM，而不是 B 站历史 API。

   理由：`temp.html` 已提供足够的卡片字段，DOM 方案不需要新增跨域权限，也能保持脚本当前权限面不变。替代方案是调用历史 API 拉取更多数据，但会引入接口稳定性、登录态、请求频率和跨域权限风险。

3. 每次同步都扫描当前已加载卡片，继续同步先滚动再等待加载稳定。

   首次点击直接扫描当前 DOM。后续点击先滚动到页面底部，然后等待卡片数量或页面高度在短时间内不再变化，再扫描当前所有已加载卡片。重复扫描旧卡片是可接受的，因为合并规则会跳过 5 个百分点以内或本地更长的记录。

4. 解析器输出统一候选记录，再交给合并器处理。

   候选记录包含 `key`、`title`、`percentNumber`、`currentTime`、`savedAt`、`sourceElement`。解析逻辑只负责从卡片抽取信息；合并逻辑只负责比较本地记录与候选记录，便于后续调整选择器或规则。

5. 分 P 优先从链接 `p=` 参数精确解析。

   卡片的 `data-bsb-bvid` 可作为基础 BV 兜底，但如果视频链接中存在 `p=` 参数，必须使用 `VideoKey.withPage(base, p)` 生成 `BV...?p=N`。如果卡片没有 `p=`，则写入基础 BV，不猜测分 P。

6. 进度比较统一使用数字百分比，阈值为绝对百分点。

   本地记录通过 `parseInt(record.percent)` 得到百分比。B 站卡片优先读取 `.bili-cover-card__progress` 的 `--bili-cover-card-progress-value` 或“已观看 N% / 已看完”，如果只有 `current/total` 形式，则按时间换算百分比。`80%` 与 `85%` 的差距为 5 个百分点，跳过；`80%` 与 `86%` 的差距为 6 个百分点，才允许远端更长记录更新本地。

7. `currentTime` 只来自真实时间文本，不从百分比伪造。

   如果卡片有 `01:01:14/01:17:14` 这类文本，则 `currentTime` 使用斜杠前的当前观看时间。如果卡片只有百分比或“已看完”，则不生成虚假的 `currentTime`。更新已有记录时，如果远端没有 `currentTime`，应保留本地已有 `currentTime`。

8. 写入规则以更长进度为准，并设置 5 个百分点跳过阈值。

   - 本地无记录：写入 B 站记录。
   - 本地有记录且差距 `abs(remotePercent - localPercent) <= 5`：完全跳过，不更新 `savedAt`。
   - B 站进度大于本地进度且差距超过 5：更新为 B 站记录。
   - B 站进度小于本地进度且差距超过 5：保留本地记录，计入跳过。

9. `savedAt` 使用历史卡片底部设备图标旁的时间文本。

   解析器需要支持“今天HH:mm”“昨天HH:mm”“MM-DD HH:mm”“YYYY-MM-DD HH:mm”等常见文本，并转换为脚本现有 `YYYY-MM-DD HH:mm:ss` 格式。无法可靠解析时跳过该卡片，不使用当前时间兜底。

10. 批量写入使用 `StorageManager.saveRecords(records, false)` 后统一 `StorageManager._notifyChange()`。

   理由：同步可能一次处理多张历史卡片，复用批量接口能减少分片写入与 UI 刷新次数。写入完成后刷新页面标记；如果脚本历史管理面板正打开，也刷新列表和统计。

## Risks / Trade-offs

- 历史页 DOM 类名或结构变化 -> 使用 `data-bsb-bvid`、视频链接、标题、进度条 CSS 变量和角落时间文本的多层兜底；无法解析时跳过并报告数量。
- DOM 方案需要用户逐次继续同步 -> 符合用户期望的按钮流程，避免一次操作无限滚动导致页面卡顿或触发站点限制。
- 时间文本存在相对日期或年份缺失 -> 只解析能可靠落到绝对日期的格式；无法解析则跳过。
- 远端只有百分比时无法续播 -> 不伪造 `currentTime`，避免跳转到错误位置；已有本地 `currentTime` 可保留。
- B 站进度小于本地进度 -> 保留本地较长进度，避免覆盖用户在当前设备的更新记录。

## Migration Plan

本次变更不改变存储 key、紧凑格式或导入导出结构，无需数据迁移。发布后用户可在 B 站历史记录页使用悬浮按钮同步当前已加载卡片，并通过继续同步逐步加载和同步更多历史。

回退策略：移除悬浮按钮、滚动等待逻辑、DOM 解析器和合并器即可；既有记录仍是脚本原有格式，不需要恢复迁移。

## Open Questions

- B 站历史页不同账号、不同实验版本下的卡片 DOM 类名可能不一致，实现时需要用真实页面验证并保留选择器降级。
