# bilibili-history-storage-consistency Specification

## Purpose

保证观看历史在多个标签页、备份恢复、导入、删除和异常退出之间保持一致，使已经成功保存的数据不会被无关记录或较旧副本覆盖，并明确不同数据来源的合并方式与失败后的恢复行为。

## Requirements

### Requirement: 多实例写入保留独立记录
系统 MUST 保留不同脚本实例成功提交的独立视频记录，包括运行于现有匹配范围内不同 Bilibili 子域的实例。

#### Scenario: 两个实例交错保存不同视频
- **WHEN** 两个实例从相同旧数据开始，交错保存两条属于同一历史分片的不同视频记录
- **THEN** 两次保存都成功后，新实例查询和导出的结果 MUST 同时包含两条记录
- **AND** 结果 MUST 不依赖用户先切回标签页或保持原实例继续运行

#### Scenario: 不同子域操作同一份历史
- **WHEN** 一个现有匹配子域的页面保存观看进度，另一个匹配子域的管理面板同时导入或删除其他视频
- **THEN** 两个已完成的操作 MUST 同时保留，且后续读取 MUST 得到一致结果

### Requirement: 数据来源具有明确的合并语义
系统 SHALL 区分播放采样时间、官方观看时间和数据提交顺序；本地有效播放采用较新的采样，官方历史同步继续遵循现有更长进度及五个百分点阈值规则，导入继续跳过已有记录。

#### Scenario: 用户从头重看
- **WHEN** 用户在已确认身份的新播放会话中从头重看，产生比已有记录更晚但百分比更低的有效进度
- **THEN** 续播位置 MUST 更新为新会话的位置，不能仅因百分比较低而拒绝保存

#### Scenario: 同一视频存在延迟到达的旧采样
- **WHEN** 同一视频较早采集的进度在较新采样之后到达
- **THEN** 较早采样 MUST 不得覆盖已经确认的较新播放位置
- **AND** 相同时间的并发采样 MUST 使用稳定的决胜规则，使所有实例最终一致

#### Scenario: 官方历史进度差值不超过阈值
- **WHEN** 官方历史候选与最新本地记录的进度差值不超过五个百分点，或者本地进度更长
- **THEN** 系统 MUST 跳过该候选，并保留本地记录的原有时间与续播位置

### Requirement: 备份按有效期和新旧关系恢复
系统 MUST 在恢复前检查备份的有效性、有效期、对应正式记录和删除状态，且只能在恢复成功或确定无需恢复后移除该备份。

#### Scenario: 旧备份不能回滚新进度
- **WHEN** 正式记录保存于较晚时间且进度为 80%，备份来自较早时间且进度为 20%
- **THEN** 恢复后正式记录 MUST 保持 80% 及其较晚时间

#### Scenario: 过期备份不会成为正式记录
- **WHEN** 一份备份已经超过现有七天有效期
- **THEN** 系统 MUST 跳过恢复，且不得先写入正式历史再清理备份

#### Scenario: 恢复写入失败
- **WHEN** 一份可恢复备份的正式提交失败
- **THEN** 备份 MUST 保留以供重试，且界面和日志不得将其报告为恢复成功

### Requirement: 删除与撤销不会被旧副本破坏
系统 SHALL 使已确认删除对旧备份和旧播放采样有效，并仅对尚未被后续操作取代的本次删除执行撤销。

#### Scenario: 删除后出现旧备份
- **WHEN** 用户已删除一条记录，随后启动的页面发现删除前生成的该记录备份
- **THEN** 该记录 MUST 保持删除状态，不得自动恢复

#### Scenario: 删除后发生新的观看
- **WHEN** 用户删除记录后重新观看同一视频并产生新的有效采样
- **THEN** 系统 MUST 允许创建新的观看记录

#### Scenario: 撤销期间已产生更新记录
- **WHEN** 用户请求撤销删除，但同一视频已经有删除之后的新记录
- **THEN** 撤销 MUST 保留新记录，并反馈跳过已变化的记录数量

### Requirement: 导入先校验后提交
系统 MUST 完整校验输入文件及其记录，再执行可见的数据修改；保留已有合法数组记录、对象记录和当前导出文件的导入能力。

#### Scenario: 文件中途出现无效记录
- **WHEN** 导入文件包含若干合法记录以及一个 `null`、非法视频 key、非法字段类型或无效时间值
- **THEN** 系统 MUST 拒绝本次导入，并指出无效记录或字段
- **AND** 正式数据、内存查询结果和页面标记 MUST 保持导入前状态

#### Scenario: 文件包含已有记录
- **WHEN** 合法文件包含当前已存在的视频记录
- **THEN** 系统 MUST 跳过这些记录，保留最新本地内容，并准确反馈新增与跳过数量

#### Scenario: 规范化后出现重复 key
- **WHEN** 同一文件中的多个 key 规范化后指向同一视频或分 P
- **THEN** 系统 MUST 在提交前提示重复项并拒绝本次导入，避免按文件遍历顺序静默覆盖

### Requirement: 提交失败与中断可恢复
系统 MUST 将一批历史修改作为可识别的提交处理；未完成的批次不得表现为已成功导入或同步，重试同一提交不得重复创建记录。

#### Scenario: 批次写入中断
- **WHEN** 导入或批量保存的数据写入中途失败，或页面在确认提交完成前关闭
- **THEN** 新实例 MUST 能区分已提交与未完成数据
- **AND** 未完成批次 MUST 不得作为完整成功结果参与历史查询与统计

#### Scenario: 内部数据整理遇到并发写入
- **WHEN** 系统清理重复内部数据时，其他实例仍在提交观看记录
- **THEN** 清理后 MUST 保留每条记录的最新有效状态与删除信息
- **AND** 在替代副本成功确认前 MUST 不得删除唯一可恢复副本

### Requirement: 既有历史与导出格式兼容
系统 MUST 保留现有视频 key、分 P key、设置 key 及历史导出对象格式；内部一致性元数据不得混入用户导出的观看记录。

#### Scenario: 已有用户升级后读取和导出
- **WHEN** 用户已有当前分片历史及设置，并首次运行新实现
- **THEN** 历史记录、续播位置和设置 MUST 可继续使用
- **AND** 导出 MUST 继续以视频 key 映射原有公开记录字段，不要求用户手工转换文件
